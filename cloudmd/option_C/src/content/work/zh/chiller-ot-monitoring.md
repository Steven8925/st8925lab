## 專案背景與限制
一台由西門子 Climatix POL687 控制器管理的磁浮離心式冰水主機，負責供應整棟五星級飯店的空調冷水。唯一的監控介面是機台上的 PLC 面板以及一顆實體警報燈。沒有歷史數據，也沒有遠端警報功能。

嚴格的限制條件：(1) 對原廠控制器零修改（維持保固），(2) 不允許停機時間（飯店 24/7 營運），(3) 預算僅有原廠/BMS 報價的八到十分之一。

## 遭遇的問題
半夜兩點發生的故障，往往要等到建築物溫度升高、客房客訴後才會被發現。維修技師每天需花費數小時進行人工巡檢。微小的異常狀況會逐漸升級為嚴重的停機事件，且完全沒有數據記錄可以追蹤。

## 評估方案與拒絕原因
- **原廠遠端監控套件**：拒絕 — 預算高達 8-10 倍，且存在被供應商綁定的風險。[待確認：確切的報價倍數]
- **全面升級 BMS 系統**：拒絕 — 針對單一資產的規模過大、前置時間長、成本高昂。
- **客製化 ESP32 解決方案（最終選擇）**：硬體成本低、無供應商綁定問題，客戶可完全掌握自身數據的所有權。

## 系統架構
```text
Turbocor Chiller (Siemens Climatix POL687)
       │  RS-485, Modbus RTU (read-only)
       ▼
ESP32 Custom PCB (Arduino core, OTA-updatable)
       │  Outbound HTTPS
       ▼
Backend + Time-Series Database
       ├──▶ Web Dashboard (歷史趨勢)
       ├──▶ Mobile Dashboard (即時狀態)
       └──▶ Alert Engine ──▶ 推播通知
```
監控參數包含：壓縮機轉速、冰水供/回水溫度、冷卻水溫度、系統壓力及故障/警報代碼。

## 最困難的部分
初版韌體成功建立了通訊連線，但讀取所有暫存器回傳的都是 0。除錯過程中發現了**四個獨立且互相疊加的缺陷**：

1. **錯誤的鮑率 (Baud Rate)**：韌體預設為 9600，而 PLC 設定為 19200。[待確認：確切數值]
2. **錯誤的功能碼 (Function Code)**：程式使用了 FC03 (Read Holding Registers)，但 PLC 的數據開放於 FC04 (Read Input Registers)。
3. **表地址與 PDU 偏移量 (Table Address vs. PDU Offset)**：原廠文件標示暫存器為 40001，但程式直接送出 40001，而沒有減去基數取得正確的 PDU 地址 0x0000。
4. **Float32 字節順序 (Word Order)**：32 位元浮點數橫跨兩個暫存器。韌體假設為 Big Endian，而 PLC 使用了 Little Endian 互換，導致即使地址正確，解碼出來的依然是亂碼。

每個錯誤都會獨立產生相同的症狀（全 0 或亂碼），讓隔離問題變得極度困難。

## 專案成果
- **故障偵測時間縮短約 80%**：自動推播警報將反應時間從數小時縮短至數分鐘。
- **巡視工時減少約 50%**：數位狀態監控取代了例行性的人工巡視。
- **連續的歷史紀錄**：從無數據到具備秒級/分級解析度的時序日誌。
- **超過 14 個月的連續穩定運作**：現場零未處理當機事件。

## 如果能重來，我會怎麼做
- 在撰寫韌體前，先建立一個 Modbus 暫存器映射驗證工具 — 這能讓地址偏移與功能碼問題在幾分鐘內被發現，而不是耗費數天。
- 增加一個可在現場抽換的 RS-485 收發器模組，以加快鮑率的測試速度。
